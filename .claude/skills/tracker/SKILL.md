# tracker

Один запуск — один прогон: обойти весь зашитый список URL, получить цену по
каждому и свести результаты в одну таблицу.

## Разделение труда

`tracker` не умеет разбирать страницы и не должен уметь. Цену с конкретной
страницы достаёт скилл **extract-price** — он один знает про форматы BYN,
рассрочку и блоки «похожие товары». Задача tracker — только три вещи:

1. пройти по списку URL,
2. на каждом URL вызвать extract-price,
3. сложить полученные объекты цены в одну таблицу прогона,
4. записать эту таблицу в репозиторий tracker-data как файл прогона.

Если понадобилось поправить разбор цены — правится extract-price, а не tracker.
Копировать сюда логику парсинга нельзя.

## Список URL

Зашит в `references/urls.txt` — 7 страниц товаров, по строке на URL. Это и есть
список прогона: пользователь ссылки не передаёт, они уже в скилле. Добавить или
убрать товар — отредактировать этот файл, менять инструкцию не нужно.

## Как действовать

1. Прочитать список: `.claude/skills/tracker/references/urls.txt`.

2. Обойти его целиком — **для каждого URL вызвать extract-price** и получить
   объект `{regular_price, sale_price, has_credit}`. Быстрый путь — прогнать
   весь список одной командой, она вызывает скрипт extract-price на каждом URL:

   ```bash
   python3 .claude/skills/tracker/scripts/run_tracker.py
   ```

   Полезные флаги: `--format json|csv|markdown`, `--urls <файл>` — другой список
   вместо зашитого. Код возврата `1` означает, что часть строк осталась без цены.

   Флаг `--out` нужен на шаге 5, чтобы собрать файл прогона для `tracker-data`;
   в репозиторий самого скилла результат не пишется — см. «Куда девать результат».

3. Добрать вручную то, что не далось скриптом. Строки со статусом, отличным от
   `ok`, — это URL, на которых нужно пройти по инструкции extract-price до конца:
   открыть страницу через WebFetch, найти цену и собрать объект руками. Строку
   из таблицы при этом не выбрасывать — заполнить её.

4. Проверить таблицу целиком, прежде чем отдавать. Здесь работают те же
   инварианты extract-price, но видно их лучше, чем на одной странице:
   `sale_price < regular_price` в каждой строке; цена, которая на порядок
   выбивается из соседних, — почти наверняка платёж по рассрочке или цена
   другого товара; `null` в `regular_price` — это не результат, а недоделанная
   строка.

5. Записать прогон в `tracker-data` — через GitHub MCP, файлом `YYYY-MM-DD.json`
   в корне репозитория, по файлу на прогон. Подробности — в
   `references/storage.md`: параметры вызова, формат файла и что делать, если
   прогон за эту дату уже есть. Коротко:

   ```bash
   python3 .claude/skills/tracker/scripts/run_tracker.py --format json --out <дата>.json
   ```

   затем `mcp__github__get_file_contents` (проверить, есть ли файл за эту дату)
   и `mcp__github__create_or_update_file` с `owner: VitaliShaklach`,
   `repo: tracker-data`, `branch: main`, `path: <дата>.json`. Дату брать
   сегодняшнюю; если часы машины расходятся с реальной датой, передать её явно
   флагом `--date`. Прогон, где не заполнено вообще ничего, сначала показать
   пользователю и спросить, коммитить ли его.

6. Отдать одну таблицу на весь прогон — по строке на товар, не семь отдельных
   ответов. Под таблицей одной строкой — сколько URL из скольких дали цену, что
   помешало остальным и ссылка на закоммиченный файл прогона.

## Куда девать результат

У результата два адресата, и путать их нельзя.

**Пользователю — в переписку.** Таблицу и сводку под ней показать прямо в ответе,
целиком. Ответ в переписке обязателен всегда, даже когда прогон уже уехал в
`tracker-data`: ссылкой на файл его не заменять.

**В историю — в `tracker-data`.** Туда и только туда коммитится запись прогона,
файлом `YYYY-MM-DD.json` (шаг 5 и `references/storage.md`).

**В репозиторий скилла — ничего.** `hexlet-vibecoding` хранит сам инструмент:
инструкцию, скрипт, тесты и список URL. Результаты прогонов в нём не лежат,
PR с ними не открывается. Локальный файл через `--out` — только если пользователь
прямо попросил, и такой файл тоже не коммитится.

## Таблица прогона

Ровно четыре колонки, по одной строке на товар — это будущая запись прогона,
её формат менять не стоит:

| # | URL | regular_price | sale_price | has_credit |
|---|-----|---------------|------------|------------|
| 1 | https://catalog.onliner.by/pump/jileks/6550prof | 1349.00 | 1199.99 | да |
| 2 | https://nasosov.by/catalog/vodomet_prof_55_35_a_df_dzhileks_6535/ | 289.50 | — | нет |

Та же таблица в `--format json` — это и есть запись прогона, которая уезжает
в `tracker-data` файлом `YYYY-MM-DD.json`: там к строкам добавлены `status` и
`note`, а пустые значения — `null`. Схема хранения и параметры коммита — в
`references/storage.md`.

Пустое значение — прочерк, а не ноль и не пустая ячейка: `sale_price` без
скидки и цена, которую не удалось получить, читаются по-разному только вместе
со сводкой под таблицей, поэтому сводка обязательна. Прогон с недобранными
строками так и называется — неполный.

## Чего не делать

- Не разбирать HTML самостоятельно и не переносить сюда куски extract-price.
- Не выкидывать строку товара из таблицы, если цену получить не удалось, —
  строка остаётся, значения прочерками, причина в сводке.
- Не выдумывать цену взамен недоступной страницы.
- Не подменять зашитый список URL тем, что вспомнилось: список только из
  `references/urls.txt`.
- Не коммитить результат прогона в репозиторий скилла и не открывать с ним PR:
  история цен уезжает только в `tracker-data`, в `hexlet-vibecoding` её нет.
- Не заводить второй файл на ту же дату: повторный прогон за день перезаписывает
  `YYYY-MM-DD.json` через `sha`, а не плодит `-2` и `-copy`.

## Проверка скилла

Офлайн-тест на фикстурах extract-price, сеть не нужна:

```bash
python3 .claude/skills/tracker/tests/test_tracker.py
```

Проверяет ровно зону ответственности tracker: все URL списка обойдены в
исходном порядке, для каждого вызван extract-price и его ответ лёг в строку,
таблица собралась, а недоступная страница дала строку с ошибкой, а не падение.
Ожидаемый результат — `OK все проверки пройдены`.
